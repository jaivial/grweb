Plan de estabilización: seguridad backend y usuarios del backoffice

Plan pragmático para corregir primero los riesgos críticos de autorización y exposición de secretos, y después estabilizar el flujo de usuarios del backoffice migrado a /var/www/grweb/backoffice/.

URL canónica: https://fer-backoffice.menustudioai.com Puerto backoffice: 5174 Backend: ASP.NET Core 8 Minimal API Frontend: Preact + Vite + TypeScript

Resumen Ejecutivo

El sistema tiene dos frentes de riesgo: controles backend insuficientes en endpoints administrativos y un flujo de usuarios del backoffice inconsistente tras la migración. La prioridad debe ser cerrar autorización, secretos y permisos multi-tenant antes de invertir en pulido visual.

Crítico Backend

Varios endpoints sensibles están protegidos solo con [Authorize], exponiendo acciones administrativas a roles como staff o registrador.

Crítico Backoffice

La página de usuarios espera un array, pero la API devuelve un objeto paginado con items y totalCount. Además hay rutas rotas por parámetros y slugs no registrados.

Problema

La autorización actual no distingue con suficiente precisión entre autenticación, rol global y permisos por competición. Esto permite accesos indebidos a funciones sensibles y dificulta auditar cambios. En paralelo, el backoffice de usuarios tiene contratos API duplicados y rutas inconsistentes que rompen listados, creación y detalle de miembros.

  • Riesgo de seguridad: staff o registradores autenticados podrían invocar endpoints administrativos no destinados a ellos.
  • Riesgo de secretos: credenciales SMTP/Gmail pueden filtrarse desde endpoints de configuración.
  • Riesgo multi-tenant: check-in e inscripciones no verifican permisos sobre la competición objetivo.
  • Riesgo operativo: el backoffice navega a rutas que no existen o lee parámetros incorrectos.
  • Riesgo de mantenimiento: hay dos contratos de miembros incompatibles y dos patrones CRUD simultáneos.

Arquitectura Objetivo

Backend seguro por defecto

  • Filtros/extensiones centralizados para Minimal APIs: RequireRootAdmin(), RequireAdminRole(), RequireCompetitionPermission().
  • Autorización aplicada por grupo de rutas y reforzada en servicios críticos.
  • Permisos tenant-aware para check-in e inscripciones usando competicionId explícito.
  • Protección de auto-eliminación centralizada en servicio, no solo en endpoints nuevos.

Gestión segura de secretos

  • Endpoints de configuración devuelven solo estado, flags y valores enmascarados.
  • Secretos crudos nunca salen por JSON ni logs.
  • Login legacy hardcoded eliminado o restringido a entorno local controlado.
  • Cookies con HttpOnly, Secure, SameSite adecuado y expiración explícita.

Contrato API único para usuarios

  • Un contrato paginado normalizado: items, totalCount, page, pageSize, totalPages.
  • Tipos frontend alineados con backend.
  • Sin duplicación de APIs de miembros en client.ts.

Backoffice route-based

  • Un flujo canónico para usuarios: preferentemente CRUD por rutas.
  • Rutas slug-aware registradas en backoffice/src/app.tsx.
  • Gates de permisos consistentes en lista, creación, detalle y rol.
  • Componentes bajo reglas frontenac: data-*, useMemo, useCallback, sin handlers inline.

Principios

  1. Seguridad antes que UX: cerrar exposición de endpoints y secretos antes del pulido frontend.
  2. Autorización centralizada: evitar repetir condiciones frágiles en cada endpoint.
  3. Defensa en profundidad: validar en filtros de endpoint y en servicios cuando el daño sea alto.
  4. Contratos explícitos: una sola forma de paginar usuarios en backend y backoffice.
  5. Backoffice canónico: cualquier cambio de usuarios se hace en backoffice/, no en frontend/.
  6. Tareas pequeñas: cada fase debe poder validarse con build, smoke tests y QA puntual.

Fases

Fase 0: Hotfix mínimo de rutas de miembros

Crítico Objetivo: hacer utilizables las rutas básicas sin abordar todavía el rediseño completo del CRUD.

  • Corregir mismatch :userId vs usuarioId.
  • Registrar rutas slug-aware usadas por navegación existente.
  • No cambiar visual ni flujo modal todavía salvo lo estrictamente necesario.

Criterios de aceptación

  • La navegación desde usuarios a detalle de miembro resuelve el parámetro correcto.
  • Las URLs con slug de competición cargan páginas existentes sin 404 interno.
  • npm run typecheck y npm run build pasan en backoffice/.

Fase 1: Cierre crítico de autorización administrativa

Crítico Objetivo: impedir que usuarios autenticados sin privilegio ejecuten endpoints administrativos.

  • Crear extensiones/filtros de autorización reutilizables para Minimal APIs.
  • Aplicar filtros a endpoints sensibles de AdminEndpoints.cs.
  • Retirar o restringir login hardcoded legacy.

Criterios de aceptación

  • Un usuario staff/registrador recibe 403 en endpoints administrativos restringidos.
  • Un root/admin autorizado conserva acceso a endpoints administrativos necesarios.
  • No queda login hardcoded disponible en producción.
  • dotnet build pasa en backend/GrCup.Api/.

Fase 2: Secretos y configuración de email

Crítico Objetivo: impedir exposición de credenciales SMTP/Gmail y corregir copy operativo.

  • Enmascarar valores sensibles en respuestas de configuración.
  • Separar lectura de estado de configuración de escritura de secretos.
  • Corregir copy de email: la cuenta ya existe, el primer acceso solo activa/establece flujo inicial.

Criterios de aceptación

  • Ninguna respuesta JSON contiene contraseña SMTP, token Gmail, secret key ni valor crudo equivalente.
  • Usuarios no autorizados reciben 403 en endpoints de escritura de configuración.
  • El email de invitación no afirma que la cuenta se crea recién en el primer acceso.
  • Smoke test confirma solo flags/valores masked como ******** o sufijos parciales seguros.

Fase 3: Permisos tenant-aware en check-in e inscripciones

Alta Objetivo: exigir permiso por competición en mutaciones operativas.

  • Agregar contexto de competición a rutas que hoy no lo tienen o derivarlo de forma segura.
  • Aplicar RequireCompetitionPermission para check-in e inscripciones admin.
  • Evitar que un usuario con acceso a una competición modifique otra.

Criterios de aceptación

  • Un registrador solo puede operar sobre competiciones asignadas.
  • Mutaciones sin competicionId validable fallan con 400 o 403 según corresponda.
  • Se mantienen contratos de respuesta compatibles para clientes actuales o se documenta la migración.
  • dotnet build y smoke tests de check-in/inscripción pasan.

Fase 4: Contrato paginado único de usuarios

Alta Objetivo: alinear frontend y backend alrededor de items/totalCount.

  • Normalizar tipos en backoffice/src/types/api.ts.
  • Eliminar duplicación incompatible en backoffice/src/api/client.ts.
  • Adaptar helpers y página de usuarios al objeto paginado.

Criterios de aceptación

  • UsersPage renderiza data.items y pagina con totalCount.
  • No existen dos métodos públicos incompatibles para listar miembros/usuarios de competición.
  • El frontend no asume array raíz para /api/competition/{competicionId}/users.
  • npm run typecheck y npm run build pasan en backoffice/.

Fase 5: Un flujo canónico de CRUD de usuarios

Alta Objetivo: elegir flujo route-based y retirar ambigüedad modal/rutas.

  • Conectar la lista a rutas de crear, detalle y rol.
  • Retirar o aislar modales CRUD si ya no son el patrón principal.
  • Aplicar gates de permisos en todas las páginas de ruta.

Criterios de aceptación

  • Crear miembro, ver detalle y editar rol se realizan por rutas canónicas.
  • Usuarios sin permiso no ven acciones ni pueden entrar directamente por URL.
  • El rol admin/root no se ofrece a usuarios no root desde UI.
  • Browser QA pasa contra https://fer-backoffice.menustudioai.com.

Fase 6: Limpieza frontenac y deuda media

Media Objetivo: dejar las páginas de usuarios conformes a las reglas de arquitectura frontend.

  • Agregar atributos data-* diferenciadores en elementos HTML.
  • Mover datos derivados a useMemo.
  • Estabilizar handlers pasados a hijos con useCallback.
  • Planificar limpieza separada de useState en layout/protected route.

Criterios de aceptación

  • Las páginas de usuarios no tienen handlers inline pasados a componentes hijos.
  • Listas, contadores, textos compuestos y clases derivadas usan useMemo.
  • Todo tag HTML editado en TSX tiene atributo data-ui, data-slot o equivalente.
  • La limpieza de useState fuera de usuarios queda como ticket separado, no mezclado.

Riesgos

  • Ruptura de clientes existentes: agregar competicionId a rutas puede requerir compatibilidad temporal o migración coordinada.
  • Permisos mal modelados: si los roles actuales no distinguen root/admin/staff/registrador con claridad, primero hay que consolidar claims.
  • Duplicidad histórica: eliminar APIs duplicadas en client.ts puede revelar dependencias ocultas.
  • QA incompleto: las pruebas manuales deben cubrir acceso directo por URL, no solo navegación normal.
  • Deuda frontend fuera de alcance: useState en layout/protected route debe tratarse después para no mezclar riesgos.

Rollback

Regla: no revertir controles de seguridad críticos para recuperar UX. Si una fase de seguridad bloquea operación legítima, ajustar claims/permisos o allowlist específica, no volver a [Authorize] genérico.

  • Backend autorización: mantener cambios en ramas pequeñas. Si falla un endpoint legítimo, revertir solo la aplicación del filtro en ese endpoint y abrir hotfix de permisos.
  • Secret masking: no volver a exponer secretos; si la UI necesita datos, añadir DTO seguro con flags o valores parcialmente enmascarados.
  • Tenant-aware routes: si una ruta nueva rompe cliente, conservar endpoint legacy temporal con permiso centralizado y marcar deprecación.
  • Frontend usuarios: si route-based falla, mantener lista operativa y desactivar enlaces rotos antes que reactivar modales inseguros.

Orden Recomendado

  1. FE-00 y FE-01: hotfix mínimo para que rutas de miembros sean navegables.
  2. BE-01, BE-02, BE-03: autorización centralizada, endpoints admin y login/cookies.
  3. BE-04 y BE-05: secretos de email y copy de invitación.
  4. BE-06 y BE-07: permisos por competición en check-in e inscripciones.
  5. BE-08: auto-protección en servicios.
  6. FE-02 y FE-03: contrato paginado único en backoffice.
  7. FE-04, FE-05 y FE-06: flujo route-based, gates y restricciones de rol.
  8. FE-07: limpieza frontenac de atributos, memorias y handlers.
  9. Validación final: dotnet build, npm run typecheck, npm run build, smoke tests API y QA navegador contra URL canónica.

Resultado esperado: backend con permisos explícitos y secretos protegidos; backoffice de usuarios navegable, tenant-aware y alineado con un contrato API paginado único.
