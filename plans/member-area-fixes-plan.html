Plan de arreglos: invitaciones y area de miembros

Objetivo: convertir la experiencia de miembros en un flujo completo y coherente con el backoffice, mejorar la invitacion por email y reemplazar modales anidados por rutas navegables con slugs, layout y breadcrumbs.

Alcance y decisiones

Esta fase evita rehacer componentes sin direccion y fija la arquitectura antes de tocar codigo.

  1. Confirmar rutas objetivo. Usar rutas bajo competition slug: /backoffice/:competicionSlug/users, /backoffice/:competicionSlug/users/roles/:roleSlug y /backoffice/:competicionSlug/users/members/:usuarioId.
  2. Definir slugs canonicos. Los roles navegables seran root, admin, staff, registrador. Roles legacy se normalizan antes de construir enlaces.
  3. Evitar modales anidados. El detalle de rol y el detalle de miembro deben ser paginas con layout, no overlays. Solo se conserva modal para acciones cortas como confirmacion de borrado si hace falta.
  4. Mantener reglas de permisos. Root puede todo. Admin puede gestionar staff y registrador, pero no admins ni root. Staff y registrador no ven la seccion.
  5. Aplicar patrones del proyecto. Todas las paginas deben usar BackofficeLayout, data attributes en tags HTML y derived data con useMemo.

Mejorar plantilla de email de invitacion

La invitacion debe verse profesional, legible en clientes de email y alineada con el backoffice.

Archivos probables

backend/GrCup.Api/Services/EmailService.cs

  1. Extraer builder de plantilla. Crear un metodo privado BuildUserInvitationEmailHtml para separar estilo/contenido de SendUserInvitationAsync.
  2. Usar HTML compatible con email. Usar tablas, estilos inline, ancho maximo 600px, fondos solidos, padding seguro y sin dependencias externas.
  3. Mejorar jerarquia visual. Header oscuro con nombre de competicion, bloque de credenciales, CTA principal, instrucciones de seguridad y footer de soporte.
  4. Agregar texto alternativo. Mantener TextBody con login URL, email, password temporal y recomendacion de cambiar contrasena.
  5. Escapar contenido dinamico. Usar WebUtility.HtmlEncode para nombre, email, competicion y password.
  6. No loguear password. El password temporal solo se manda al destinatario, nunca a logs ni respuestas API.

Direccion visual recomendada

  • Fondo general gris claro #f4f5f7.
  • Tarjeta blanca con header negro/tinta.
  • CTA rojo o negro, texto claro y alto contraste.
  • Bloque de credenciales con borde suave y monospace para password.
  • Footer con aviso: "Si no esperabas esta invitacion, ignora este email".

URL del boton Iniciar sesion desde variable de entorno

El href del CTA de email debe depender de website_frontend_url. Por ahora el valor esperado es fer-backoffice.menustudioai.com.

  1. Leer variable exacta. En backend usar Environment.GetEnvironmentVariable("website_frontend_url").
  2. Agregar fallback seguro. Si no existe, usar https://fer-backoffice.menustudioai.com durante esta etapa.
  3. Normalizar protocolo. Si la variable viene como fer-backoffice.menustudioai.com, convertir a https://fer-backoffice.menustudioai.com.
  4. Construir URL final. El boton debe apuntar a {website_frontend_url}/backoffice/login.
  5. Configurar entorno Docker. Agregar website_frontend_url=fer-backoffice.menustudioai.com al archivo de entorno usado por grcup-api o al compose si corresponde.
  6. Validar en email. Enviar invitacion de prueba y confirmar que el href contiene dominio correcto, protocolo correcto y ruta login.
private static string GetBackofficeLoginUrl()
{
    var baseUrl = Environment.GetEnvironmentVariable("website_frontend_url")
        ?? "https://fer-backoffice.menustudioai.com";

    if (!baseUrl.StartsWith("http://") && !baseUrl.StartsWith("https://"))
        baseUrl = $"https://{baseUrl}";

    return $"{baseUrl.TrimEnd('/')}/backoffice/login";
}

Dos pestanas en el area de miembros: Roles y Miembros

La pagina principal debe organizarse en dos vistas claras para evitar mezclar overview de roles con tabla de usuarios.

Archivos probables

backoffice/src/pages/backoffice/users/*, backoffice/src/app.tsx, backoffice/src/layouts/BackofficeLayout.tsx

  1. Crear estado de tab en URL. Preferir rutas o query param: /users?tab=roles y /users?tab=members. Si se usa estado local, debe sincronizarse con URL para deep-link.
  2. Tab Roles. Mostrar cards de root, admin, staff, registrador con contador, descripcion corta y botones de accion.
  3. Tab Miembros. Mostrar tabla/lista de miembros con busqueda, rol, estado de invitacion y accion primaria para ver detalle.
  4. Usar iconos lucide-react. En cards de roles usar botones con iconos como Eye para ver rol, UserPlus para anadir miembro en ese rol y Shield o Users para indicar permisos.
  5. Mejorar affordance UX. La card completa puede ser clickable, pero debe tener botones visibles: "Ver rol" y "Anadir". Evitar que el usuario tenga que adivinar que la card abre algo.
  6. Responsivo. Tabs en mobile deben ser botones full-width o scroll horizontal con touch targets de minimo 44px.
  7. Accesibilidad. Usar role="tablist", role="tab", aria-selected y foco visible.

Reemplazar detailed views en modal por rutas con slugs y breadcrumbs

La mejor solucion es convertir los detailed views en paginas reales. Esto elimina modales anidados, mejora navegacion, permite compartir enlaces y respeta el layout del backoffice.

Rutas nuevas

  • /backoffice/:competicionSlug/users: pagina principal con tabs Roles y Miembros.
  • /backoffice/:competicionSlug/users/roles/:roleSlug: detalle de rol.
  • /backoffice/:competicionSlug/users/members/:usuarioId: detalle de miembro.
  • /backoffice/:competicionSlug/users/new?role=staff: alta de miembro con rol preseleccionado.

Detalle de rol

  1. Crear pagina RoleDetailPage. Debe usar BackofficeLayout y leer roleSlug desde router.
  2. Breadcrumbs. Mostrar: Backoffice / Miembros / Roles / Staff.
  3. Header de rol. Mostrar nombre, descripcion, contador, capabilities y restricciones.
  4. Lista de miembros. Mostrar miembros filtrados por rol con accion para ir a detalle de miembro.
  5. Acciones. Boton "Anadir miembro" navega a /users/new?role=:roleSlug.
  6. Estados vacios. Si no hay miembros en el rol, mostrar empty state con CTA de anadir si el usuario puede gestionar.

Detalle de miembro

  1. Crear pagina MemberDetailPage. Debe usar BackofficeLayout, leer usuarioId y cargar el miembro.
  2. Breadcrumbs. Mostrar: Backoffice / Miembros / Nombre del miembro.
  3. Vista principal. Mostrar datos de usuario, rol, estado de invitacion, email, fecha de invitacion y quien lo invito.
  4. Editar rol. Select con roles permitidos segun actor: root puede todos; admin solo staff/registrador.
  5. Eliminar miembro. Boton con confirmacion. Admin no puede eliminar admins ni root.
  6. Guardar cambios. Usar endpoint PUT /api/competition/{id}/users/{usuarioId}/role y mostrar toast de exito/error.

Alta de miembro

  1. Crear pagina NewMemberPage. Debe aceptar query ?role=staff para preseleccionar rol desde una card.
  2. Formulario. Campos: nombre, email, password, rol. Validar email y password minimo 8 caracteres.
  3. Submit. Usar endpoint POST /api/competition/{id}/users.
  4. Post-submit. Redirigir a detalle del miembro creado o volver a Miembros con toast.

Contratos API y ajustes necesarios

Las rutas detail necesitan datos especificos y errores claros para que la UX no dependa de cargar toda la lista siempre.

  1. Verificar endpoint detail. Confirmar GET /api/competition/{id}/users/{usuarioId} devuelve un solo miembro.
  2. Crear respuesta consistente. Mantener { success: true, data: ... } y errores { success: false, message: ... }.
  3. POST debe devolver miembro creado. La respuesta debe incluir usuarioId para redirigir a detalle.
  4. Errores 403 claros. Si admin intenta editar admin/root, devolver mensaje util: "No puedes modificar usuarios admin o root".
  5. Email no debe bloquear UX. Si crear usuario funciona pero email falla, decidir si se devuelve warning o success con mensaje. Recomendado: success con warning logged y toast informativo si backend lo expone.

Validacion, build y tunnel

Despues de implementar, validar backend, frontend y tunnel publico.

Backend

  1. Ejecutar dotnet build en backend/GrCup.Api.
  2. Rebuild/restart API con Docker Compose.
  3. Verificar http://localhost:5006/api/health.
  4. Crear usuario de prueba y verificar email recibido.

Frontend

  1. Ejecutar npm run typecheck en backoffice.
  2. Ejecutar npm run build en backoffice.
  3. Reiniciar preview en :5173 si el tunnel sirve el build.
  4. Verificar https://fer-backoffice.menustudioai.com/backoffice/fer/users.

Browser QA

  1. Login como root y confirmar que ve Miembros en todos los competition IDs.
  2. Login como admin y confirmar que ve Miembros solo en competitions asignadas.
  3. Login como staff y confirmar que no ve Miembros ni puede acceder por URL directa.
  4. Login como registrador y confirmar que solo ve QR.
  5. Probar tabs Roles y Miembros en desktop y mobile.
  6. Probar rutas detail con refresh del navegador.
